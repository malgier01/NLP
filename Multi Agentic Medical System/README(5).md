# Multi-agent explanation and evaluation of medical answers (engineering thesis)

My engineering thesis: a multi-agent workflow that **explains** and **evaluates** answers
generated by a large language model to clinical questions about **multiple sclerosis (MS)**.

The system has three layers:

1. **Generation:** an LLM answers clinical questions about MS.
2. **Explanation:** 4 agents (two medical LLMs, each with and without PubMed retrieval)
   explain the medical reasoning behind each answer.
3. **Evaluation:** 5 evaluation agents grade the answers using the universal criteria
   from OpenAI's HealthBench, one agent per criteria axis.

Notebook: [`praca_inzynierska.ipynb`](praca_inzynierska.ipynb)

## Data

55 clinical questions about multiple sclerosis in Polish (from patients' and clinicians'
perspectives), each with a reference answer written by an expert.

## Layer 1: generation

`gemini-3-pro-preview` answers each Polish question in English, acting as a senior medical
consultant.

## Layer 2: explanation agents

| Agent | Model | Knowledge source |
|---|---|---|
| BioMistral + RAG | BioMistral-7B (bf16) | model knowledge + PubMed abstracts |
| BioMistral without RAG | BioMistral-7B (bf16) | model knowledge only |
| Meditron + RAG | Meditron-70B (4-bit NF4) | model knowledge + PubMed abstracts |
| Meditron without RAG | Meditron-70B (4-bit NF4) | model knowledge only |

Each agent receives an answer from layer 1 and writes a single-paragraph medical
justification. RAG agents search PubMed and cite the retrieved papers.

**Running the models.** Meditron-70B needs about 140 GB of memory in bf16 and repeatedly
crashed the environment. It runs in **4-bit NF4 quantization with double quantization**
(bitsandbytes), split across two GPUs with `device_map="auto"` and a per-GPU memory limit.

**Prompting base models.** Both models are base models without instruction tuning: they
continue text rather than follow instructions. I used **completion-style prompting with
prefilling**: the prompt starts the answer ("The medical reasoning behind the step taken in
the scenario is ...") and the model continues it. The citation format for RAG answers is
forced the same way. This guarantees that a source is cited, but not that the source
supports the claim.

## Layer 3: evaluation agents

- **Criteria:** the universal (cluster-level) criteria from the HealthBench consensus set,
  used verbatim and grouped into 5 axes: *accuracy, completeness, context awareness,
  instruction following, communication quality*.
- **Scoring:** binary. 1 if the answer fulfils the criterion, 0 otherwise.
  HealthBench inspired the method; the scores are not comparable with HealthBench's
  published numbers.
- **Judge:** Gemini 2.5 Flash returns a JSON score with a one-sentence explanation.
- **Choosing the criterion for an answer**, two variants in the notebook:
  1. Gemini function calling: each criterion is a tool the agent can call;
  2. embedding routing: the criterion most similar to the answer
     (`paraphrase-multilingual-MiniLM-L12-v2`, cosine similarity) is chosen for each axis.

## Context: what the thesis focused on, and what came after

Most of the effort went into running the two medical models at all: quantization, the
environment, and prompting base models. Retrieval got the least attention and turned
out to be the weakest part. After the defense I reviewed it and redesigned it in a
separate notebook.

**Problems in the thesis retrieval:**
- the query was the first 6 words left after removing stopwords, joined with AND: often
  no results, or results that matched by accident;
- digits and hyphens were removed, so medical terms broke (`anti-CD20` became `anti`);
- the first 3 PubMed results were always used, without any relevance check;
- the model received the first 800 characters of the plain-text record, which mostly
  contains authors and affiliations rather than the abstract;
- errors from PubMed were passed to the model as if they were evidence.

**New approach (`search_pubmed_v2`, a drop-in replacement):**
1. **Broad search:** multiple sclerosis is required, and up to 8 keywords are joined with
   OR, with medical tokens kept whole. 20 candidates in English, with an abstract, from 2010.
2. **Relevance scoring** with a biomedical embedding model (`S-PubMedBert-MS-MARCO`).
3. **Selection:** the 3 best papers above a similarity threshold. If nothing fits, the
   agent gets no evidence instead of irrelevant evidence.

The full abstracts are fetched in one XML request, and every search is logged (keywords,
query, PMIDs, scores, errors). The agent code does not change.

**Other issues found after the defense:**
- **Criterion routing could be effectively random.** The criteria were ordered with
  `set()`, whose order changes between Python sessions, and were matched by position to
  embeddings saved in an earlier session. In addition, the embedding model reads only
  about 128 tokens, so routing on question + answer mostly saw the question.
  Fix: sorted criteria, embeddings computed in the same session, routing on the answer only.
- **Not compared yet:** the explanations of the four agents were generated, but the
  thesis does not compare them with each other.
- **Same model family:** the judge (Gemini 2.5 Flash) and the answer model (Gemini 3 Pro)
  come from one family, so self-preference bias is possible.

## Next steps

- Evaluate the new retrieval: blind relevance labels for retrieved papers (precision@3),
  old vs new.
- Compare the four explanation agents with the evaluation layer, using the same criteria
  for every answer.
- Turn retrieval into a tool that an agent calls by itself, with the LLM writing the
  PubMed query (this would also work for questions in Polish). A LangChain/LangGraph
  version is planned.
- Use instruction-tuned medical models where available.

## Tech stack

Python, Hugging Face Transformers, bitsandbytes (4-bit NF4), Biopython (NCBI E-utilities),
sentence-transformers, Google Gemini API (generation, function calling, judging), pandas.
Run on Google Colab and a multi-GPU cloud machine.
